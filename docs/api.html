API reference

Endpoints a network offers so StarChat can use the features it lists in its discovery file. Every feature is optional: a network leaves out the endpoints of features it does not list, and the client hides them.

All paths are relative to apiBaseUrl from the discovery file. Requests and answers are JSON unless noted. The client sends Accept: application/json and no cookies, so the API has to answer cross-origin requests (Access-Control-Allow-Origin: * or the calling origin, Authorization as allowed header).

Times are ISO 8601. Channel names start with # and are compared in lower case.

Errors with 422 carry Laravel style messages ({ "message": "…", "errors": { "field": ["…"] } }), the client shows the first one. A request with a missing or expired token is answered with 401.

The same as OpenAPI 3.1.0: openapi.yaml. The features and where the API address comes from are described in Discovery file.

login

Only with bearer or api-login in auth. The API accepts the token as Authorization: Bearer <token>. With bearer the IRC server also accepts it with SASL IRCV3BEARER. With Ergo this is a JWT signed with a key from accounts.jwt-auth, the account name in sub. With api-login the token is only for the API and the client logs in on IRC with SASL PLAIN, so any string the API recognizes works.

A page that embeds the chat can also hand over a token itself (mountChat({ bearer })), then this endpoint is not called. Guests have no token, so features that need one stay hidden for them.

POSTlogin

Token for an account. No token.

With bearer in auth the client then logs in on IRC with IRCV3BEARER instead of PLAIN. With api-login it keeps PLAIN on IRC and uses the token only for the API. Without either, this endpoint is not used.

Body:

FieldTypeRequiredMeaning

{
  "username": "alice",
  "password": "secret"
}
StatusMeaning
200Logged in.
401Wrong name or password.

Answer 200:

FieldTypeRequiredMeaning

nicknamestringNick to use on IRC. Without it the client keeps the one typed in.
{
  "token": "eyJhbGciOiJIUzI1NiJ9…",
  "nickname": "alice"

push

Only used by app builds (shell: 'mobile'): the app cannot receive Web Push itself, so the network relays it to Firebase Cloud Messaging. Browsers register directly with the IRC server (draft/webpush) and do not call these endpoints.

The client hands the endpoint to the IRC server with WEBPUSH REGISTER <endpoint> p256dh=…;auth=…, using the keys the app created. The IRC server sends encrypted pushes to the endpoint, the network forwards them unchanged to FCM and the app decrypts them. How app and chat talk to each other is described in Features.

A token belongs to one install: registering it again moves it to the current account.

}

GETchat/voice/filters

Microphone filters. Needs a token.

Optional noise filters the client can load. The client ships the AudioWorklet of each filter it knows, the network hosts the WebAssembly files with Access-Control-Allow-Origin: * (the desktop app loads them from file://). Unknown ids are ignored, so a new build of a filter gets a new id (rnnoise-v2) and older clients keep loading theirs. rnnoise-v1 pairs with the files of @sapphi-red/web-noise-suppressor 0.4.1. An empty list or an error leaves the browser's own noise suppression.

StatusMeaning
200Offered filters, possibly none.
401No token, or the token is invalid or expired.
404Voice is not set up on this network.

Answer 200:

FieldTypeRequiredMeaning
filtersarray of objectyes
filters[].idstringyes
filters[].wasmURLyes
filters[].wasm_simdURLBuild for CPUs with WebAssembly SIMD, used when available.
